# Changelog

All of YorvoID's packages are released together, with the same version ([compatibility](docs/compatibility.md)). Each release lists what changed, and what to do where a change breaks covered code.

## [Unreleased]

### Added

- `RetryableConflict`: a deadlock or serialization failure in YorvoID's work. `Operations::run()` decides and runs an operation again, up to 3 times, when its transaction conflicts; inside the application's transaction it throws, for the application to retry. In Symfony, a request that ends with one gets 503 with `Retry-After` ([storage](docs/concepts/storage.md#when-transactions-conflict)).
- `Transactions::retrying()`, and `ForgetsWhatItRead`, which `VersionedCache`, `CachedPolicyStore` and `CachedRelationStore` implement: what forgets what the request read before work runs again. Only a conflict on an attempt before the last drops what the attempt left waiting for the end; any other failure, the last conflict or a lost connection runs it. `TransactionsContract` checks `retrying()`.
- `ChangesAuthority`, `DeclaresEffects`, `DeclaredEffects`, `Effect`, `EffectPart`, `AttributeChange` and `HoldsAuthority` (`@experimental`): a command that changes authority says so, and its package declares what it gives and takes. `PolicyEffects` declares those of roles, groups, attributes and relations ([authorization](docs/concepts/authorization.md)).
- `AuthorizationDecorator`: an `Authorization` around another, which forwards everything and keeps every check `Operations` makes when it's built; override `decide()` or `decideConsequence()` to trace or to refuse more ([the decision point](docs/concepts/operations-and-events.md#the-decision-point)).
- `AppliesToConsequences`: a forbid that's also evaluated when its operation runs as another's consequence.
- `yorvoid:log:verify --decisions` also checks that every entry citing a decision cites a permit the decision log holds, with that hash: a permit from a second decision point that records nothing is reported.
- `yorvoid.decisionPoint`, a PHPStan rule in `yorvoid/phpstan-rules`: flags `new Operations(...)` in an application.
- Concurrency contracts in `yorvoid/testing`, run in several processes by `Race` from a factory file of yours: `OneTimeTokenStoreConcurrencyContract`, `RecoveryCodeStoreConcurrencyContract`, `SetupStoreConcurrencyContract`, `CeremonyStoreConcurrencyContract`, `ThrottleStoreConcurrencyContract`, `PrincipalStoreConcurrencyContract`, `SessionStoreConcurrencyContract`, `SecurityLogStoreConcurrencyContract` and `VerifierStoreConcurrencyContract`. `#[ConcurrencyTestedIn]` names the test case that runs one, and `#[InMemoryStores]` says a test case has none to run ([storage](docs/concepts/storage.md#requests-at-the-same-moment)).
- `VerifierStoreContract` and `VerifierLogContract`, for the verifier's stores. `yorvoid/testing` suggests `yorvoid/intent-verifier` for them.
- `Transactions::afterEnd()`: runs once the outermost transaction has ended, committed or rolled back. `TransactionsContract` checks it.
- Decision digests: `yorvoid:log:checkpoint` first appends `yorvoid.decision.digest` with the decision records written since the last one (`DecisionDigests`), and `yorvoid:log:verify --decisions` checks them. `yorvoid.decision_log.digest_grace` (a minute) is how long a record may take to be written. `DecisionDigests::take()` returns how many records the digest covers.
- `DecisionRecorded`: dispatched for each decision record written, refusals and failed attempts among them.
- `SecurityLog::attempt()` and `AttemptLog`: failed attempts and refusals, kept apart from the chain.
- `ForgetRoles`, `ForgetRelations` and `ForgetAttributes` (`yorvoid.role.forget_all`, `yorvoid.relation.forget_all`, `yorvoid.attribute.forget_all`): a deletion's consequences, run by `ForgetRolesOfDeletedPrincipals`, `ForgetRelationsOfDeletedPrincipals` and `ForgetAttributesOfDeletedPrincipals`, which are their handlers.
- Consequence-only operations for what only another operation may cause: `StepUpSession` (`yorvoid.session.step_up`), `StartCoolDown` (`yorvoid.recovery.cool_down`), `DisableCredential` (`yorvoid.credential.disable`) and `ForgetCredentials` (`yorvoid.credential.forget_all`). A way of stepping up of your own is an operation that causes `yorvoid.session.step_up` ([sessions](docs/concepts/sessions.md#starting-a-session)).
- `StepUpWithPasskey` (`yorvoid.passkey.step_up`): a passkey step-up is an operation, decided and recorded like a sign-in.
- `yorvoid/phpstan-rules`, PHPStan rules for an application: `yorvoid.storeCall` flags a call to one of YorvoID's stores, `yorvoid.internalUse` a use of what YorvoID marks `@internal` ([how-to](docs/how-to/phpstan-rules.md)).
- `@spi` marks the interfaces you implement and don't call: YorvoID's stores ([interfaces you implement](docs/compatibility.md#interfaces-you-implement)).
- `AuditFailed::SECURITY_NOTICE`: a security notification that couldn't be sent. `SecurityNotifications` takes an event dispatcher for it.
- `ProvesActors` and `StoredSessions`: every decision proves its actor first, a session by reading it from its store ([actors](docs/concepts/operations-and-events.md#actors)). In Symfony, a service tagged `yorvoid.actor_prover` proves an actor class of your own.
- `yorvoid.api.paths`: path prefixes whose requests have the `api` origin, as do those with an `Authorization: Bearer` header.
- `@experimental`: `ActsUnderDelegation`, `Request::$execution` and `Request::$purpose`, the shapes of M3's delegation.
- `Transactions::lockRealm()`: locks a realm until the transaction ends, for a check over the realm as a whole, e.g. that it keeps an administrator, and every change that can break one. Changes of status, claiming a setup, creating an active principal, and every change of roles, groups, abilities, relations and attributes take it first ([locks](docs/concepts/storage.md#locks)).
- `Transactions::beforeCommit()`: runs a callback just before the outermost transaction commits, inside it; if it fails, nothing commits.
- `YORVOID_LOCK_ORDER=check`: in your tests, every transaction on a connection with `TransactionMiddleware` throws when it takes YorvoID's locks out of their order ([locks](docs/concepts/storage.md#locks)).

### Breaking

- `Transactions` adds `retrying()`: a `Transactions` of your own implements it. A deadlock in YorvoID's work is a `RetryableConflict`, with DBAL's `DeadlockException` as its previous, rather than the `DeadlockException` itself. `Operations` takes the `Transactions` it retries in (`transactions:`).
- `NoEscalation` and `StepUpForSensitiveChanges` weigh a change by its declared effect: a command that changes authority but whose effect nothing declares makes them Indeterminate, and `Operations` refuses to be built with one in its catalogue. Each takes the effects to read (`$effects`), the policy package's if not given. `PolicyStore`, `RelationStore` and `AttributeStore` extend `HoldsAuthority`, which has no methods.
- `Operation\Authorization` adds `decideConsequence()`, `requireForbids()`, `checkCatalogue()` and `decidesOffline()`: `Operations` asks them of any `Authorization`, and no longer checks for the Evaluator. An `Authorization` of your own implements them, or extends `AuthorizationDecorator`.
- Only the Evaluator makes a `Decision` that permits: its constructor is private, and `Decision::permit()` is gone. A decision that permits is for the command and actor it was made for, and `Operations` issues on it once: an `Authorization` that gives one back for another request, e.g. from a cache, throws an `IntegratorError`. `identified()` and `recorded()` throw for a decision that permits, and a `Decision` can't be unserialized. An `Authorization` of your own refuses with `Decision::deny()` or `Decision::indeterminate()`, or returns the Evaluator's decision.
- Each consequence of an operation is decided by the `Authorization` that permitted the operation, and has a decision of its own, recorded under the operation's: a consequence's permit carries its own decision ID, and the decision log has one more record per consequence. `DecisionRecord` is format 3, with `parent`; format 1 and 2 records still read and verify.
- Every store contract but `FlowStoreContract` asks for `transactions()`, the transactions the store takes part in, and runs the store inside them: a write in a failed transaction is gone, a write is seen in its own, and a write that changes nothing or is refused leaves the transaction usable. A store on a connection of its own now fails them. A store contract that has a concurrency contract fails until the test case runs it, names the one that does (`#[ConcurrencyTestedIn]`), or is marked `#[InMemoryStores]`.
- Refusals and failed attempts are no longer entries of the security log (D-42): a refused operation, a code, token, link or passkey that didn't work, a refused signature, a throttled form. They're decision records (`kind: attempt` for those that aren't an operation's decision), written outside the application's transaction and without the realm's lock. `SecurityLogEntryRecorded` listeners no longer see them: listen to `DecisionRecorded`. Without a decision log (`SecurityLog` given no `attempts:`), they're entries as before.
- `DecisionRecord` is format 2 (attempts with their details; the read set's slot); format-1 records still read and verify. `DecisionLogStore::add()` takes whether the records are written apart from any caller's transaction, and the store adds `now()`, `written()`, `digestedUntil()`, `digested()` and `prunedBefore()`; a migration adds `written_us` and two tables.
- `Transactions` adds `afterEnd()`: a `Transactions` of your own implements it, and a callback's failure goes no further than raising your alert. `DbalTransactions` and `InMemoryTransactions` take an event dispatcher and a logger for it (`AuditFailed::AFTER_END`).
- `yorvoid.audit.on_failure: refuse` needs `yorvoid.decision_log.connection`: the bundle refuses to start without it.
- The passkey sign-in and step-up name `yorvoid.credential.disable` in `causes`.
- An evaluator decides on an actor only once it's proven (D-45): give `Evaluator::builtIn()` `actors: [new StoredSessions($sessionStore)]`, or a session's decisions are Indeterminate (`unproven_actor`, a new case of `IndeterminateReason`), as are those of an actor class nothing proves. The decision reads the stored session, its authentication factors included.
- A step-up is only ever a refused decision: removing a credential, replacing the recovery codes and registering a passkey ask their proof in `StepUpSelfService`, which refuses with a `StepUpRemedy` or, after a recovery, a `WaitRemedy`, before the operation is permitted and recorded. Their handlers no longer throw `StepUpRequired` or `HeldAfterRecovery`: catch `NotPermitted` and read its remedies. `StepUpSelfService` takes `Credentials` (`credentials:`), to tell a first set of recovery codes, which asks a recent proof as any new credential does, from one replacing the owner's, which asks a phishing-resistant proof and waits out a recovery; without it, every set asks that. `StepUpRequired` and `HeldAfterRecovery` remain for what checks a session before any operation, e.g. `Passkeys::beginRegistration()`.
- `Operations::run()` refuses an `ActingPrincipal`, which acts only in a permit's consequences. `Permit::cause()` and `Permit::consequence()` take `actingAs:` as a `PrincipalId`, and `ActingPrincipal`'s constructor is `@internal`.
- `new Origin(OriginKind::System)` throws: only YorvoID's own work is the System. `Origin` is no longer a `readonly` class; its properties still are.
- An after-commit callback, e.g. a listener of an "-ed" event, that fails is logged at error and no longer thrown, from `Transactions::run()` or from the application's commit: the work it waited for is committed (D-43). The remaining callbacks still run. A `Transactions` of your own reports such a failure the same way.
- A security notification that can't be sent raises the audit alert (`AuditFailed::SECURITY_NOTICE`, logged at critical), not an error log entry: a missed security notice is an audit fact.
- The constructors of the events YorvoID's listeners act on are `@internal`: `PrincipalCreated`, `PrincipalStatusChanging`, `IdentifierChanged`, `CredentialAdded`, `CredentialRemoving`, `CredentialRemoved`, `NewDeviceSignedIn`, `RecoveryCodeUsed`, `RecoveryCodesGenerated`, `RecoveryLinkUsed` and `SignedOperationRan`. Listen to them as before; YorvoID makes them.
- `ForgetCredentialsOfDeletedPrincipals` takes only `Credentials`: give `Credentials` the `RecoveryCodeStore` (`recoveryCodes:`), and forgetting a deleted principal's credentials removes its recovery codes too.
- `SecurityNotifications::signedOperation()` and `Database::deleteInBatches()` are `@internal`.
- A passkey step-up runs through `Operations`: `$operations->run(new StepUpWithPasskey($realm, $ceremonyId, $response), $session, $origin)` instead of `Passkeys::finishStepUp($session, ...)`, which is now its handler. `StepUpStep` takes `Operations` as its second argument.
- `Sessions::stepUp()`, `StepUp::startCoolDown()`, `Credentials::disable()` and `Credentials::forgetAll()` (was `forgetAllOf()`) are handlers of those consequences and take a `Permit`, so only the operation that causes them runs them.
- A `PolicyStore` of your own increments the realm's version in every change, before it writes (`PolicyStoreContract::testEveryChangeIncrementsTheVersion`), so caches never read an older policy than what's stored; `bump()` stays, as the lock a change takes before it reads what it changes.
- `CredentialStore::update()` is gone. A store writes only what each change is about: `rename()` the label, `markUsed()` the last use, of an active credential only, and `disable()` the status. Each says whether it changed anything. A store of your own implements the three; `CredentialStoreContract` checks them, with a second instance over the same data (`sameCredentialStore()`), which you override for a store processes share.
- `Credentials::markUsed()` takes the realm and the credential's ID, returns whether the credential was still active, and is `@internal`: it's for the packages that check credentials.
- In Symfony, YorvoID's stores are services under IDs of their own, `yorvoid.store.<name>` (e.g. `yorvoid.store.session`), and no longer under their interfaces or classes: your services don't get a store by autowiring. A store of your own replaces YorvoID's by aliasing its ID, not its interface ([stores of your own](docs/concepts/storage.md#stores-of-your-own)).
- `SecurityLog::record()` returns nothing. Inside a transaction on a connection with `TransactionMiddleware`, the entry is appended just before the commit, so it has no sequence or hash until then; if appending fails, the commit throws and nothing of the transaction is committed. Read entries from `SecurityLogStore::entries()`.
- `SecurityLog::lock()` is removed: lock with `Transactions::lockRealm()`, the first lock of the unit of work.
- `Transactions` adds `lockRealm()` and `beforeCommit()`: a `Transactions` of your own implements them. `lockRealm()` must be a write that conflicts under REPEATABLE READ and can be taken again in the same transaction; doing nothing is right only for storage that runs one writer at a time. `beforeCommit()` returns false, and runs nothing, where it can't see the commit.
- `PrincipalStore` adds `lock()`, a write that locks the principal's row until the transaction ends, e.g. an update of a counter column: a store of your own implements it. The migrations add `principal.lock_count` and the `realm_lock` table.
- `Credentials` takes `Principals`, as its third argument.
- `DbalTransactions` takes the `StorageLocation` (`location:`) when YorvoID's tables aren't in the default place; the Symfony bundle passes it.
- Inside a transaction you opened through DBAL's `transactional()`, a failure appending the security log at your commit may reach you as `NoActiveTransaction`, with the cause as its previous. It isn't retried.

### Security

- A refusal survives the application's rollback and takes no realm lock, and a decision log that can't be written gives `NotPermitted` and the audit alert, not a storage error (AR-03).
- A copied passkey stays disabled when the application's transaction rolls back with the refusal (ARC-0058). It's disabled once that transaction has ended, committed or rolled back, in a transaction of its own; if that fails, the audit alert says which passkey is still active.
- A deletion's listeners run on its permit and only for the principal it deletes, and the events YorvoID's listeners act on can't be made by an application: a made-up event no longer removes someone's roles, relations, attributes or passkey, or sends them a security notification.
- A Permit is never refused afterwards for a missing step-up: the decision log no longer says Permit for an operation its handler then refused.
- Actors prove themselves (AR-05, D-45): a hand-built `Session` that isn't on record, has ended or expired, or is another principal's decides nothing, nor does a forged authentication factor; an application can't run an operation as anyone by naming them in an `ActingPrincipal` (L-4), nor act as the host's operator everywhere by claiming the System origin (ARC-0016).
- What only an operation may cause takes its permit (D-41, AR-01): a session's step-up, a recovery's cool-down, disabling and forgetting credentials. A step-up is about the principal who proved who they are, and can't step up anyone else's session.
- Cache freshness after a policy change no longer depends on callers: every `PolicyStore` change increments the version itself (SS-05).
- YorvoID's stores are marked `@spi`: implement them, don't call them. A call changes YorvoID's records without a decision or a log entry, as writing the database does ([interfaces you implement](docs/compatibility.md#interfaces-you-implement)). The Symfony bridge doesn't give them to application code (AR-01).
- `Sessions::refresh()` records each new token in the security log (`yorvoid.session.refresh`), as a sign-in and a step-up do: it issues a credential (AR-01).
- A passkey or a set of recovery codes disabled during a sign-in that uses it, e.g. by a "This wasn't me" report, stays disabled. Before, the sign-in wrote back its own copy of the credential, active, and went on. Now the sign-in is refused and recorded, and a recovery code it would have used is kept (ARC-0057).
- A change of status no longer runs its guard rules against a role, group, relation or attribute change made at the same moment, which could leave a realm without its last administrator: both take the realm's lock. Changes of one principal (tokens, recovery codes and links, adding, removing and disabling credentials, starting a session) take turns on the principal's lock, and a disable no longer slips in between a sign-in's read and its use of the credential. A realm's security log is locked only while its entries are appended at the commit, so changes in one realm no longer wait for each other's whole unit of work.

### Fixed

- Adding a relation that exists, or any insert a store refuses as a duplicate, no longer aborts the PostgreSQL transaction it runs in: the stores insert with `ON CONFLICT` on the key they expect, and a conflict on another key still throws. Policy and relation versions are made or incremented in one statement.
- YorvoID's `TransactionMiddleware` rolls back before it runs what waits for the end of the transaction.
- After a commit the application started (`$connection->commit()`, `transactional()`, Doctrine's `wrapInTransaction()`, Messenger's `doctrine_transaction`), YorvoID's after-commit callbacks can open transactions: each runs in one of its own (ARC-0059, D-43). Before, they failed while DBAL still counted the committed transaction (PostgreSQL 25P01): a security notification after such a sign-in wasn't sent, and the application's `commit()` threw after its data had committed (`NoActiveTransaction`). A callback that leaves a transaction open is rolled back and reported, and the connection stays usable.
- The stores convert values through the connection (`Connection::convertToPHPValue()`), not `Type::getType()`, which Doctrine DBAL 4.6 deprecates: no deprecations with DBAL 4.6.
- `yorvoid/policy-testing` suggests `symfony/config` with the other packages its Symfony bundle needs: Symfony's `Bundle` doesn't load without it.

## [0.4.0] - 2026-11-13

Every operation runs through one decision point: `Operations::run()` asks the evaluator, and gives its handler a permit. Abilities, roles, relations, groups and attributes in `yorvoid/policy` and `yorvoid/relations`, with policy tests and mutation testing in `yorvoid/policy-testing`; the decision log; a FIPS mode and ES256 keys; refusals people can act on; and the fixes from the authorization audit (M2-13).

### Breaking

- In Symfony, `isGranted()` for a declared ability refuses a subject that doesn't say which resource it's about with an `IntegratorError`, rather than deciding without the resource: an ID, an array, or an object that implements neither `ConcernsResource` nor the new `ConcernsNoResource`. Give a `ResourceRef`, such an object, or `[ResourceRef, object]` ([the subject](docs/concepts/authorization.md#the-subject)); an object your rules read that is about no resource implements `ConcernsNoResource`. The `Request`, as `access_control` asks, decides on the whole realm and is no longer the subject rules read. Other voters no longer grant a declared ability (each is wrapped in `AbstainOnYorvoIDAbilities`); their refusals still count. `decideMany()` takes `[ResourceRef, object]` only as a list of exactly those two.
- Services take a `Permit` where they took an actor or a session (`Principals`, `Sessions`, `Credentials`, `Invitations`, `SetupCodes`, `RecoveryCodes`, `RecoveryLinks`, `Passkeys`, `NotMe`): run operations with `$operations->run($command, $actor, $origin)`, where the actor is the signed-in `Session` or, on the host, `Operator`. A handler called directly, without a permit from `Operations`, doesn't run.
- `#[Operation]` takes what authorizes the operation (`AuthorizedBy`), and its command implements `Command`; one people run on their own account implements `SelfOperation`. `OperationDescription` says what authorizes the operation and what it causes.
- Signing in, claiming a setup code, accepting an invitation, using a recovery code or link, confirming an email address and "This wasn't me" are commands run through `Operations` (`SignInWithPasskey`, `ClaimSetup`, `AcceptInvitation`, `RecoverWithCode`, `RedeemRecoveryCode`, `UseRecoveryLink`, `VerifyEmail`, `ReportNotMe`), as is registering a passkey (`RegisterPasskey`). Claiming and accepting sign the person in and return their session.
- `StartSession`, `AddCredential` and `VerifyIdentifier` run only as a consequence of another operation, e.g. a sign-in.
- `OwnIdentifiers` is gone: someone changes their own email address or username with `SetIdentifier` through `Operations`, and `StepUpSelfService` asks for the recent proof it needed.
- Principals' events (`PrincipalCreating`, `PrincipalCreated`, `PrincipalStatusChanging`, `PrincipalStatusChanged`, `IdentifierChanging`, `IdentifierChanged`) carry the operation's permit; `EmailVerification::send()` takes the permit of the operation that set the address, and `EmailVerification::principalCreated()` sends the link for a principal created active.
- `SecurityNotifications` takes `Operations` instead of `OneTimeTokens`; `PasskeyFlows`, its steps (`PasskeySignInStep`, `PasskeyRegistrationStep`, `SetupCodeStep`, `InvitationStep`, `RecoveryCodeStep`, `RecoveryCodesStep`, `RecoveryLinkStep`, `EmailVerificationStep`), `CurrentSession`, the authenticators (`PasskeyAuthenticator`, `RecoveryCodeAuthenticator`, `RecoveryLinkAuthenticator`) and `Scenario` take `Operations`.
- `Operations` with `PolicyChanges`, `GroupChanges`, `RelationChanges` or `AttributeChanges` builds only on the `Evaluator`, holding the forbids those handlers require (`RequiresForbids`): with an `Authorization` of your own, or one decorating the evaluator, it fails to build. In Symfony, `Authorization` is the evaluator already.
- `IssueToken` and `RevokeTokens` refuse YorvoID's own purposes (`yorvoid.*`, e.g. `yorvoid.recovery_link`) with `NotPermitted`, the operator's included: a token for one is issued or revoked only by the operation it belongs to (`IssueRecoveryLink`, `Invite`, `ResendInvitation`, `WithdrawInvitation`, an address change or a new principal for email verification, `IssueNotMeLink`). Issue your own tokens under your own namespace.
- A consequence of an operation that's about a principal (`ConcernsPrincipal`) must be about the operation's own, and each consequence runs as many times as `causes` names it, once by default: an operation that runs one twice names it twice. A handler whose command isn't about a principal says whom it's about with `Permit::about()` before it causes anything about them.
- A change to one's own account asks what the self-service policy asks of it whatever permits it, not only on the `Self` basis: a role with `yorvoid.principals.manage` changes its own email address with a recent proof and not during a recovery's hold, as anyone does. Without a self-service policy (`NoSelfService`), an administrator changes their own address, or suspends themselves, only through someone else or the operator. `SelfServicePolicy::decide()` takes any `Command`, a `SelfOperation` or one about the actor's own principal (`ConcernsPrincipal`).
- `Checkpoints` takes `KeyRings`, each realm's signing keys, instead of one `KeyRing`: pass `new SharedKeyRings($ring)` for what it did before.
- `RelationStore::version()` is new, and every change to relations increments the realm's relations version: a store of your own keeps one (`RelationStoreContract`).
- `PolicyStore::version()` and `RelationStore::version()` must be read from what the store holds, so every process reads the same: never a counter of the process's own. The contracts check it with a second instance over the same data (`samePolicyStore()`, `sameRelationStore()`; override them for a store processes share).
- `yorvoid/core` requires `ext-openssl` instead of `ext-sodium`: signing keys sign, and the hashes security depends on are computed, through OpenSSL ([cryptography](docs/concepts/cryptography.md)). Keys, signatures and hashes are byte-identical to before. `yorvoid/passkeys` and `yorvoid/intent-verifier` require `ext-sodium`, which the WebAuthn library verifies EdDSA passkeys with.

### Added

- `ConcernsNoResource`, a subject that a decision reads but that is about no resource. In Symfony, `RequestOrigins`, the origin of what YorvoID does in a request, with one correlation ID for the request and its sub-requests, and a "Symfony voters" line in `yorvoid:doctor`, naming the voters that can't grant a declared ability.
- `ConcernsPrincipal`, a command about one principal, and `Permit::about()`. `IssueNotMeLink` (`yorvoid.not_me.issue`, the operator only), which issues the token of a security notification's "this wasn't me" link.
- `Operations`, `Permit`, `NotPermitted`, and the actors `Operator`, `Anonymous` and `ActingPrincipal`. In Symfony, the application's own `OperationHandler`s are registered.
- The evaluator (`Evaluator`): Permit, Deny or Indeterminate by the precedence of forbids, the actor's authority and permits ([authorization](docs/concepts/authorization.md)). YorvoID's ways to authorize are its built-in permits, with `SelfServicePolicy` and optionally an `AbilityPolicy`; your own rules are `PermitElement`s and `ForbidElement`s, registered by themselves in Symfony. `PrincipalAuthority` refuses a principal that isn't active.
- A decision carries its reasons, what couldn't be established (`IndeterminateReason`), and on a Deny for want of evidence its remedies (`StepUpRemedy`, `WaitRemedy`): a step-up asked by `StepUpSelfService` comes as a remedy on `NotPermitted`, not as `StepUpRequired`.
- An Indeterminate decision is logged as a warning.
- A store that can't be reached makes a decision Indeterminate with the reason `store_unreachable` (`StoreUnreachable`): a refused or lost connection, a statement's timeout, a failover. A store of your own throws `StoreUnreachable` itself.
- Offline decisions, off by default: an `OfflineDecider` may give Permit-offline while a store is unreachable, a verdict of its own that only operations declaring `#[Operation(acceptsOffline: true)]` run on; their permit says it was offline (`Permit::$offline`), and the log records `yorvoid.decision.offline`.
- A refused operation is recorded in the security log.
- An operation declares what it causes (`#[Operation(causes: [...])]`), and its permit gives consequences for those only.
- The host's operator acts from a console or job origin only when PHP runs from the command line.
- Signing keys for each realm (`KeyRings`, `SharedKeyRings`, `PerRealmKeyRings`): a realm's checkpoints are signed and verified with its own ring. In Symfony, `keys.per_realm` and `keys.directory`, `yorvoid:keys:rotate --realm`, and the doctor reports a realm without keys.
- The stores' contracts in `yorvoid/testing` (`YorvoID\Testing\Contract`): the tests YorvoID's own stores pass, one trait for each store and one for `Transactions`, for a store of your own to pass too. `yorvoid/testing` requires PHPUnit 12 or 13, and `yorvoid/flows` for `FlowStoreContract`, the tests of a `FlowStore`.
- `yorvoid/policy`: declared abilities and roles (`PolicyDeclarations`, `Ability`, `Role`), super roles, strict abilities, the `everyone` role, a realm's changes to the defaults kept as differences (`AbilityChanges`), roles created in a realm, roles assigned in a realm or on one resource with an expiry (`RoleAssignment`), roles from a `RoleSource`, and rules in PHP that permit, forbid or can't tell (`Rule`). The role permit (`RolePermit`) decides operations that need an ability; `Policy` decides an application's own abilities, in Symfony also through `isGranted()` ([authorization](docs/concepts/authorization.md#abilities)).
- A request can be about an ability on a resource (`ResourceRef`) instead of an operation: `Evaluator::decideAbility()`. A command about one resource implements `ConcernsResource`.
- A request about an ability carries its subject, the application's own object (`Request::$subject`), for rules and attribute resolvers to read, e.g. a page's author for "edit your own": the resource is the one it concerns (`ConcernsResource`) unless given, and it's never recorded, logged or cached. `isGranted()` passes any object other than a `ResourceRef` as the subject ([the subject](docs/concepts/authorization.md#the-subject)).
- Explanations (experimental): what each element's truth rests on (`Ground`: the roles that have the ability and how, the relation, the rule and the attributes it read, a proof, the actor's status), the row of the precedence that decided (`Decision::$precedence`), and `Explanation::of()` putting them together for an explainer to build its own text from ([explanations](docs/concepts/authorization.md#explanations)).
- `Policy::whyNot()` (experimental): why an actor may not do something, and the roles, relations and forbids that would change it, never who holds them. - `yorvoid/policy-testing` (experimental, for development): policy tests, the decisions an application's policy must give as cases (`PolicyCase`, `PolicyCases`), run on the policy as production builds it with its stores in memory: in Symfony from the application's container in the `yorvoid_policy` environment (`YorvoIDPolicyTestingBundle`, `yorvoid:policy:test`), without it from production's own function (`PolicyUnderTest::of()`, `vendor/bin/yorvoid-policy`), and in PHPUnit (`PolicyCasesTest`) ([test your policy](docs/how-to/test-your-policy.md)).
- Policy mutation testing (experimental, AUZ-045): `yorvoid:policy:mutate` and `vendor/bin/yorvoid-policy mutate` break the policy one change at a time (14 operators on roles, grants, groups, parents, a relation's implications, forbids, permits and the authority check) and report what no case catches, and what no case reaches, with `--min-score` and `--ignore` by stable IDs (`PolicyMutation`, `Mutants`) ([mutation testing](docs/how-to/test-your-policy.md#mutation-testing)).
- `RelationSchema::types()`: every resource type the schema declares.
- A deleted principal's roles are taken.
- The policy changes through operations (`yorvoid.role.*`, `yorvoid.ability.*`, `PolicyChanges`), each in the security log and incrementing the realm's policy version. Nobody gives or takes what they don't hold (`NoEscalation`), weighed by what a change does: a group as its roles, a link (`parent`, or one others are inherited through) as what it brings along, deleting a group or a role as what it takes away (M2-13). Giving a strict ability or a super role, directly or through what follows from it, and setting or removing a security attribute take a recent proof whatever permits the change (`StepUpForSensitiveChanges`, `StepUpCheck`, `SessionStepUpCheck`); taking never does. Both rules are required, whatever permits the changes: neither the evaluator with `RolePermit` or `RelationPermit`, nor `Operations` with `PolicyChanges`, `GroupChanges`, `RelationChanges` or `AttributeChanges`, is built without them (`RequiresForbids`). A forbid that holds for want of evidence (`Truth::holdsUnless()`) carries its remedies when they'd be enough.
- A policy element can check the operations when `Operations` is built (`ChecksCatalogue`): the role permit refuses an operation whose ability isn't declared.
- Every behaviour model is replayed against the code: the setup claim (by the order its transactions commit in) and the intent verifier's keys, as the one-time tokens were; the decision model and its fixtures in two configurations, the default and every extension point engaged (XP-16), the default's outcomes unchanged ([formal models](spec/README.md)). Inside `Verifier`, which is unchanged, its keys and the checks of what the browser answers are parts of their own (`KeyRegistry`, `IntentChecks`, internal).
- [Performance](docs/reference/performance.md): the targets (OPS-042), what each release measures, and how to measure it yourself (`composer bench`, on PostgreSQL).
- `yorvoid/relations`: relations between resources (ReBAC, AUZ-011): declared per resource type, implied by others, inherited from parents, to subject sets; checked a level at a time and at most 16 levels deep (`Relations`), with abilities they give on their resource (`RelationPermit`) and changes through `yorvoid.relation.add` and `.remove`. A role on a resource counts for what's within it. A reserved type's relations (`ResourceType(reserved: true)`, e.g. groups) change only through its owner's operations (`ReservedRelation`) ([relations](docs/concepts/authorization.md#relations)).
- Groups (IDN-056): nested, with roles given to them (`yorvoid.group.*`, `GroupChanges`, `GroupRelations`).
- Security attributes of principals (IDN-055) and attributes of the request through resolvers (AUZ-013): `SecurityAttribute`, `AttributeDeclarations`, `Attributes`, `AttributeResolver`, and `yorvoid.attribute.set` with its own ability, `yorvoid.attributes.manage`; nobody but the operator sets their own. What isn't known is Indeterminate (`missing_data`), as is any exception implementing `MissingData` ([attributes](docs/concepts/authorization.md#attributes)).
- The decision log (AUZ-040), apart from the security log and without a lock (`DecisionLog`, `DecisionLogStore`, `DecisionRecord`, `PermitRecording`): every operation's decision before it runs, abilities' refusals and Indeterminate, and their permits as configured (`yorvoid.decision_log.permits`, `sample_rate`; `Ability::$recordsPermits`). Security-log entries cite the decision that let their operation run, by ID and hash. `yorvoid:purge --keep-decisions` prunes it ([decision log](docs/concepts/security-log.md#the-decision-log)).
- Batch decisions: `Policy::decideMany()` decides an ability on many resources at one moment, each with its subject if given, with what roles, relations and the principal need read once for all (`Decisions`, `Evaluator::decideAbilities()`, `Relations::checkMany()`, `ancestorsOfMany()`); an element of your own reads for a batch by implementing `Preloads` (experimental) ([many at once](docs/concepts/authorization.md#many-at-once)).
- What decisions read is read once a request, at the realm's versions, and kept in a shared pool if one is given (`VersionedCache`, `CachedPolicyStore`, `CachedRelationStore`): keys start with the installation's ID (`Installation`, the `installation` table) and the realm; a pool that fails is passed over. In Symfony, the pool `yorvoid.cache`, on `cache.app`, or the one `cache.pool` names ([what a request reads](docs/concepts/authorization.md#what-a-request-reads)).
- Each decision has an ID, a time and the versions it read (`Decision::$id`, `$at`, `$versions`, `VersionSource`, `PolicyVersion`, `RelationsVersion`); the permit of an operation carries its decision's ID.
- Elapsed time that can't go backwards (XP-14, experimental): `Elapsed`, `Instant` and `BootTime` (the boot's clock, which counts suspended time; per process without `/proc`), `MockElapsed` in `yorvoid/testing`. `WithinOfflineLimit` decorates an `OfflineDecider`: Permit-offline only while the time since a mark is under a limit, measured so that a changed wall clock or a reboot can't extend it ([offline limits](docs/concepts/authorization.md#offline-limits)).

An unknown fact is missing data (Indeterminate) by default; with `new OrderedConditions(pessimistic: true)` (`ordered_conditions.pessimistic` in Symfony) it's decided at its worst ([ordered conditions](docs/concepts/authorization.md#ordered-conditions)).
- The audit alert (AUD-006): every audit record that can't be written, in the security log, the decision log, the intent verifier's log or a checkpoint, raises a `critical` log entry and an `AuditFailed` event; the verifier tells its notifier (`audit_failed`). A failed write of waiting decisions is reported this way, where it was an error before.
- Refusing without a record (AUD-006): with `AuditFailure::Refuse` (`audit.on_failure: refuse`), every recorded decision is written before it's returned, and a Permit whose record can't be written is Indeterminate, with the new reason `audit_unavailable`. `DbalDecisionLogStore` can write on a connection of its own (`decision_log.connection`), which a rollback of the application's doesn't take back ([when a record can't be written](docs/concepts/security-log.md#when-a-record-cant-be-written)).
- A crypto policy with a FIPS mode (CRY-01): `CryptoPolicy`, `CryptoMode`, `CryptoProvider` (`crypto.mode: fips`). The FIPS mode starts only with OpenSSL's FIPS provider alone active, and passkeys (`PasskeyPolicy::$algorithms`) and the intent verifier (`VerifierConfig::$algorithms`) use only the algorithms it allows ([cryptography](docs/concepts/cryptography.md)).
- ES256 signing keys (`KeyAlgorithm::ES256`, `yorvoid:keys:rotate --algorithm`), for a FIPS provider without EdDSA, and anchors: a checkpoint signed only once the log verifies against every checkpoint before it (`Checkpoints::anchor()`, `yorvoid:log:anchor`), which covers Ed25519 checkpoints such a provider can't check ([moving to ES256](docs/concepts/keys.md#moving-to-es256)).
- A recorded run on a FIPS-enabled operating system before each release, and `tools/fips-host/run.sh`, which does it on a throwaway AlmaLinux 9 host: 0.4.0's ran on AlmaLinux 9.8 with its build of Red Hat's FIPS provider, the tests with Ed25519 keys among them ([FIPS runs](assurance/fips-runs.md)).
- `yorvoid:doctor` checks the audit mode, the crypto mode and the keys' algorithms, and says what a check found after its name.
- Refusals for people (M2-10): in Symfony, a `NotPermitted` nothing catches is answered with a page, or JSON, of what would satisfy it: "Confirm it's you" with a button to the step-up, which comes back to the page, or how long to wait. A Deny is a 403 and what couldn't be decided a 503, never with the decision's reason; the decision's ID is shown as a reference (`refused.html.twig`, `yorvoid_remedies()`, `remedies.pages`). The step-up flow takes `return`, a path on this site. The browser client has the error code `not_permitted` and `notPermitted()` ([refusals for people](docs/concepts/symfony.md#refusals-for-people)).
- `WaitRemedy` says why it waits (`WaitReason`, in its parameters as `reason`): YorvoID's waits after an account recovery say so, and the refusal page tells the person why ([remedies](docs/concepts/authorization.md#remedies)).

### Changed

- A flow is bound to the session it runs in, the one it started in or the one it signed in and handed over, and ends, deleted, when the request doesn't have that session or a session it holds back stops being valid; an ended flow answers like an unknown one. So a flow whose held-back session ended now ends, where it went on without that session, and once a flow hands its session over, its remaining steps run only in that session. A flow started by someone not signed in is still its bearer's. Signing out keeping the PHP session (`signOutKeepingData()`, `invalidate_session: false`) also removes YorvoID's flows from it.
- `CurrentSession::hold()` and `signOut()` take `?Origin $origin = null`, the request's origin from `RequestOrigins` unless given, where they made a new one.
- In Symfony, the reason a vote for a declared ability gives is its verdict and its decision's ID (`YorvoID: Deny (decision …).`), which `AccessDeniedException`'s message shows; the decision log keeps why.

### Security

- Before 0.4.0, from the authorization audit (M2-13): with `logout.invalidate_session: false`, an unfinished flow outlived signing out: the recovery-codes page left unconfirmed answered the next person in the browser with the same codes, and one of them signed in as their owner from anywhere. A flow begun in someone's session also stayed open to the next person who signed in in the same browser, showing the first one's account name. A flow now lives within the session it runs in and ends with it, and signing out takes YorvoID's flows out of the PHP session.
- Before 0.4.0, from the authorization audit (M2-13): in Symfony, `isGranted()` with an ID, an array or an object that doesn't implement `ConcernsResource` decided without the resource, so a forbid or a rule on it didn't apply and a role on the whole realm, or one everyone has, permitted it: `isGranted('acme.pages.view', 'locked')` was granted where the locked page is refused. Under Symfony's default `affirmative` strategy, another voter that supported a declared ability granted it over YorvoID's Deny, forbids and Indeterminate included. And the Deny's reason, which forbid refused, was in `AccessDeniedException`'s message, for debug pages, logs and API errors to show.
- Before 0.4.0, from the authorization audit (M2-13): giving a role that has a strict ability, adding to a group with one (its own roles and those of the groups it's within), resetting a revoked strict default back, and a relation that gives one now take a recent proof, as does setting or removing a security attribute. So does any such change a rule, an `AbilityPolicy` or a relation permits, which skipped it before. Setting and resetting abilities are weighed by what they change. An application whose rules gave such things without a proof now sees a Deny with a step-up remedy.
- Before 0.4.0, from the authorization audit (M2-13): a principal with `yorvoid.principals.manage` changed or removed its own email address with a stale session, or in the 24 hours after a recovery, because the step-up and the hold were asked only on the `Self` basis. They're now asked of every change to one's own account, whatever permits it; suspending or deleting oneself and issuing oneself a recovery link or a token are held the same way.
- Before 0.4.0, from the authorization audit (M2-13): `IssueToken` issued any purpose with `yorvoid.principals.manage`, YorvoID's own included, for any lifetime: a recovery link for anyone, past the strict `yorvoid.principals.recover` and its 24-hour cap, or a "this wasn't me" link that disabled someone's sign-in method. YorvoID's purposes now belong to their operations; a refusal is in the security log and, since a rollback can take that record, a warning in the logger `OneTimeTokens` takes. A listener handed an operation's permit could cause its consequences about anyone, any number of times: now about the operation's own principal only, as many times as declared.
- Before 0.4.0, from the authorization audit (M2-13): two reads of relations or groups whose IDs spelled each other, e.g. a group whose ID held `#` and `|`, shared one cache entry, in a request and in a shared pool, so one could read another's memberships. `VersionedCache` encodes a read's arguments itself, and its keys start with `yorvoid.v2`, so the old entries are never read. An entry from the pool is read only if it answers the read, and memberships take only the tuples about those asked. The in-memory relation store told such tuples apart by their written form too, and now by their parts; the store contract checks it (`RelationStoreContract`).

### Fixed

- In Symfony, a request's decisions share one correlation ID, so the decision log samples a request's permits whole or not at all, as it said, and a request's decisions can be found together: each `isGranted()` had one of its own.
- Signing out, here or everywhere, works without a self-service policy (`NoSelfService`), which refused it.
- The recovery pages say they sign you out "on your other devices and browsers", not "everywhere else", and the emails after a recovery code or link say "your other devices and browsers were signed out", not "everyone else".
- The packages require each other at the version they're released with (`^0.4` for 0.4), so a release installs as a set. 0.2.0 and 0.3.0 required `^0.1` of each other and don't install together from Packagist: stay on 0.1.0, or take 0.4.0. Every release now checks this before it's published, and installs from Packagist afterwards.

## [0.2.0] - 2026-11-05

Stricter passkey and intent checks, signed checkpoints of the security log, Symfony 7.4 LTS next to 8.1, and two new packages: `yorvoid/notifications` and `yorvoid/intent-signing`.

### Breaking

- `SessionStore::stepUp()` takes the factor to add and returns the stored context with it, or null; a store of your own adds the factor itself, with a compare-and-swap on the token.
- `PrincipalStore::hasActive()`, `KnownDeviceStore::isKnown()` and the intent verifier's `VerifierLog::usedNonce()` are new: a store or log of your own implements them.
- `PasskeyStore::update()` returns whether it recorded the sign-in: a store of your own records it only over a lower counter, or a counter of 0, in one step.
- `SessionEndReason::Replaced` and `Refusal::TooManyWaiting` are new cases: a `match` over either handles them.
- `AuthenticationFactor::NO_OPERATION` records a step-up for no operation: it counts only for requirements that name none, not for every operation.
- `yorvoid/symfony` requires DoctrineBundle and FrameworkBundle, which it always needed.
- The bundle refuses at boot a configuration it would refuse later: a wrong realm, table prefix, duration, limit, origin, cookie name, script or notification address.
- `NotificationSettings` and email actions accept `https://` addresses only (`http://` for `localhost`), without a user before the host.
- A setup code works only while the realm has no active principal.
- Security notifications (`SecurityNotifications`, with its `Translations`), "This wasn't me" (`NotMe`, `NotMeReported`) and `EmailVerification` moved from `yorvoid/authn` to the new `yorvoid/notifications` (namespace `YorvoID\Notifications`); signed intents' `IntentSigning`, `IntentSummaries`, `IntentSummary`, `SignedOperationNotification` and `SignedOperationRan` from `yorvoid/passkeys` to the new `yorvoid/intent-signing` (`YorvoID\IntentSigning`). `yorvoid/authn` no longer requires `yorvoid/mail`, nor `yorvoid/passkeys` the intent verifier. Require the new packages if you use what moved; `yorvoid/symfony` requires both.
- `CeremonyStore::take()` takes the session asking: a store of your own returns a ceremony only to the session that began it, and one begun outside a session only without one.
- `ThrottleStore::advance()` replaces `replace()`: a store of your own counts an attempt, or refuses it, in one atomic step, so attempts at the same moment don't refuse each other.
- Email addresses are compared in one Unicode form (NFC), with only A–Z in lowercase and the domain in its ASCII form (IDNA); an address whose domain has no valid ASCII form is refused; `yorvoid/core` requires `ext-intl`. Addresses beyond ASCII stored by 0.1 are found again after `yorvoid:identifiers:normalize` (or `IdentifierRenormalization::run()`): run it once after upgrading, with `--dry-run` first.

### Security

- Passkeys check what the WebAuthn library leaves to them: the ceremony type, cross-origin answers, the public key, the counter with a compare-and-swap, and backup eligibility; ceremonies and flows started per address are limited.
- The intent verifier checks answers, nonces and parameters itself, and caps waiting intents.
- The intent verifier reads the browser's answers by hand into one fixed shape: Symfony Serializer's reflection-driven denormalizers no longer see what the console relays.
- Signing in again ends the session the browser held; two step-ups at once both keep their proof.
- Failed setup codes and tokens, limits reached, and passkey sign-ins and step-ups refused before the passkey is known (an expired ceremony, an unknown passkey), are recorded in the security log.
- The key file is replaced only by a complete, synced copy; Symfony's dumper shows secrets redacted.
- `yorvoid:doctor` warns on PostgreSQL while the application's database user can update, delete or truncate the security log.
- Signed checkpoints of the security log, kept outside the database (`Checkpoints`, `FileCheckpoints`, `LoggerCheckpoints`; in Symfony `yorvoid.log.checkpoint_file`, `yorvoid:log:checkpoint` and `yorvoid:log:verify`): verification finds entries cut off the end, and a history rewritten with its chain recomputed, up to the last checkpoint.
- Another session, or a sign-in, can't use up a session's passkey ceremony; links from other sites can't push the flow in progress out of the browser's session.

### Added

- `SignInEntryPoint` for the firewall; `yorvoid:keys:rotate --public`; `StepResult::reopen()` and `StepFailed` for flow steps.
- The recovery-link page names the account; the step-up page says what it confirms, and takes `within`; the signing page names the passkeys that can sign.
- Each release is a GitHub release with every package's source, its CycloneDX SBOM, and build provenance; only a signed tag is released.
- Symfony 7.4 LTS is supported next to 8.1, and PHP 8.4 next to 8.5, so YorvoID installs in Laravel 12 and Drupal 11 applications.
- `Sessions::check()` gives a valid session with its principal; the Symfony bridge loads the principal once a request instead of twice.
- `FlowSource` in the Symfony bridge adds an application's own flows, and the ones a request may start.

### Fixed

- Flows end in a problem, not an error, when a proof lapses, an operation waits out a recovery's cool-down, or someone has no passkey to confirm with.
- A failing mailer is logged, and fails neither a sign-in nor the change it's about.
